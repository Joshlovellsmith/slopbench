# Round 0 performance methodology, design 0.1.0

This is a workload specification, not a load generator. Families are evaluated
and reported separately. No composite language score is defined. Correctness
qualification against the same contract/fixture is required before ranking any
performance measurements. A candidate that answers quickly with wrong results
has zero qualifying successful operations, not an improved latency rank.

## Shared experimental controls

Workload IDs: `PERF-CAT`, `PERF-INV`, `PERF-ORD`, `PERF-ANA`, `PERF-IMP`, `PERF-SIM`.
Use Milestone 1 fixture Small/Medium/Large profiles, seed 12345 unless a recorded
experiment explicitly changes it. Record both fixture hashes, source hash,
image digest, exact development metadata when known, build/startup duration,
SQLite journal mode when observable, host CPU model/kernel/core allocation,
memory/swap/PID limits, storage device/filesystem and cache conditions. Candidate
DB internals/index names are not correctness requirements. Use a dedicated
Docker host with isolated controller CPU resources; retain its limitations.
No fixtures or large histories are generated by install or ordinary test commands.

**Common history recipe H(N):** with products/customers in fixture ID order,
select active ones only. Set all active product stocks to 1,000,000,000 through
HTTP adjustments before seeding. For order index i=0..N-1, ID is
`o-history-{i}`, customer is activeCustomers[i mod customerCount], first product
is activeProducts[i mod productCount], second is the next active product cyclically
(there are at least two). Each quantity is 1+(i mod 3). orderedAt is
`2024-01-01T00:00:00.000Z + (i mod 365)*86400000 + floor(i/365)` milliseconds.
Create through public HTTP, verify every response, and save the request ledger
and its SHA-256. This deterministically spreads data across a year. Setup is
excluded from measured request latency but separately recorded. Orders snapshot
fixture prices/categories. Failed setup invalidates that campaign. This recipe
requires no extra fixture format or candidate-specific SQL inserts.

For request selection use the existing fixture v1 LCG with seed 12345, unsigned
32-bit arithmetic, starting fresh each phase. Enumerate draws and requests in
logical request order, independent of completion order. Uniform choice is
word modulo count. Popularity choice uses word modulo the sum of fixture
popularityWeight and the first ascending-ID cumulative weight greater than that
residue. Reject inactive selections for ordering by using a prefiltered active
array and its own weight sum. No redraw loops dependent on runtime state.
A payload ledger (or its generator version/parameters/hash) records exact draws,
IDs, bodies and intended timestamps. Scheduling and data draws use separate PRNG
streams; arrival schedule below requires no random stream.

## Arrival schedule, omission and stopping

For short HTTP requests, use an **open-loop** fixed-rate schedule: intended
arrival i occurs at t0+floor(i*1e9/rate) nanoseconds for an integer rate. Start
rates 10,25,50,100,250,500,1000,2000,4000 requests/second, extending by doubling
only while safe. Per phase warm for 30 seconds at the intended rate and measure
120 seconds. Repeat three independently reset phases per rate; report spread
and confidence intervals from independent repetitions, not just pooled requests.

Schedule independently of completions. Record intended arrival, actual dispatch,
first byte and complete validated response using a monotonic clock. Primary
end-to-end latency is completion minus **intended arrival**, including controller
queuing. Also report dispatch-to-completion service latency and dispatch lag.
Do not pause arrivals when the candidate slows, replace timeouts with missing
samples, or compute percentiles only for successful fast requests. This explicitly
accounts for coordinated omission. Report successful response percentiles and
all-attempt completion/censoring distributions separately. No synthetic latency
"correction" replaces the actual scheduled timestamps.

Limit outstanding client work to 10,000 and controller dispatch lag to 5 seconds.
On exceeding either, mark the phase overloaded/controller-limited, retain planned
but undispatched arrivals as failures with reasons, and stop rather than buffering
unboundedly. Controller CPU or network bottlenecks invalidate capacity inference.
Short-request deadline is 30 seconds from intended arrival. Drain after the final
scheduled arrival up to that deadline; unfinished requests are censored timeouts,
not discarded. Halt a rate search on persistent incorrect responses, resource
kill, two overloaded phases or 80% host-memory pressure. Record the stopping
reason; never infer correctness merely from HTTP 2xx.

Default latency budgets for exploratory comparison: catalogue p99 100 ms,
inventory/order p99 250 ms, analytics p99 1000 ms. These are workload SLOs, not
functional contract requirements. Publish curves, not a single arbitrary winner.
Latency saturation means the first reproducible rate violating the family's SLO.
Throughput saturation means successful throughput plateaus despite increased
accepted offered load. Resource exhaustion means a measured memory/PID/disk/timeout
limit, reported separately. They can occur at different rates.

## Measurement and audit recommendations

* Keep per-request or bounded histogram series in JSON/sidecar artifacts, not in
  SQLite metadata rows. Persist validated shared result v1 with benchmark/suite
  versions. Missing RSS/CPU/allocation measurements remain absent, never zero.
* p50/p95/p99: report estimator (nearest rank), N, window, outcome inclusion and
  censoring. Avoid p99 claims for fewer than 1000 successful observations. Export
  attempted/success/error/timeout counts and rate in stated wall-clock seconds.
* Read CPU usage from the candidate cgroup before/after the measured phase;
  CPU time per success is delta CPU seconds/validated successes. Include GC/runtime
  background work; don't subtract an unmeasured baseline. Build/controller CPU
  are separate. Report host contention/steal conditions when available.
* Sample cgroup memory/RSS at 10 ms where feasible and report sampling interval,
  cgroup peak plus steady-state median/p95 and whether file cache is included.
  Runtime-specific allocation/GC counters are optional diagnostic supplements,
  never mandatory language-specific correctness interfaces. Record bytes allocated
  per operation only when actually measured; sampling may miss transient peaks.
* Record database/main/WAL/temp file sizes before/after, fsync/write/read bytes and
  device I/O counters where available. Distinguish logical SQLite file growth from
  physical device work, especially under page cache and copy-on-write storage.
* Measure build as isolated build start-to-exit and startup as runtime launch-to-
  validated readiness, separately from warm request timings. Include input loading
  in fresh-database startup; distinguish restart-with-existing-DB cost. Record
  dependency network exceptions, image cache state, copied source and fixture hashes.
* Record 503/timeout/OOM/exit status distinctly. Correctness assertion failures are
  not infrastructure failures; controller congestion is not candidate latency.
* Reconcile final state through HTTP and order ledgers. Independently verify CPU
  output against numerical oracles/golden vectors and smaller cross-checks; a
  separate evaluator should compute expected larger results outside timed runs.
  A hash of unverified output alone does not establish numerical correctness.
